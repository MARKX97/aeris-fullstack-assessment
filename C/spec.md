# Task C Spec — Xero Integration Review（书面方案）

> 状态：Draft v1。本任务是**论述题**：spec 定义每个问题"强答案必须包含什么"与"如何判定合格"，答案本体在 `C/answers.md`（实现阶段产出）。
> 依据：`BRIEF.md` §4。题面要求：简洁、可观测的检查、失败处理、安全生产行为；允许伪代码；**必须引用 Xero 官方最新文档**。

---

## 1. 问题陈述

针对"多租户服务同步内部订单系统与 Xero 发票、后台 worker 执行、按机构存储 token / 租户 ID / 同步游标"这一场景，回答 C1–C6 六问。考察点不是 API 背诵，而是**诊断路径、可恢复设计、生产纪律**。

## 2. Non-goals

- 不写可运行代码（伪代码 / 片段允许）。
- 不覆盖发票之外的实体（联系人、账目等）——仅作行文需要时提及。
- 不给出未经文档证实的 API 细节；**无法核实的表述必须标注为假设**（Harness 纪律：禁止编造证据）。

## 3. 全局写作约束

- 每问 150–300 词 + 可选伪代码；总篇幅以"审阅者 10 分钟读完"为准。
- 每问结尾一行 `Evidence:` 列出所依据的 Xero 官方文档主题（见 §5 文档范围）。
- 每问涉及不确定行为处显式写 `Assumption:`。

## 4. 每问要素清单（答案结构的硬性要求）

### C1 — Connection verification（连接校验）
必答要素：
- [ ] 给出**最小调用序列**（从本地 token 校验 → 租户选择 → 一次便宜的受租户限定的读操作），每步说明"证明什么"。
- [ ] 明确区分三个不同层面的证明：token 本身有效（OAuth 资源服务器接受）、目标租户已连接（出现在 connections 列表）、对该租户有数据权限（租户级读成功）。
- [ ] 每步的失败形态与对应处置（哪个环节坏了修什么）。
- [ ] 明确"最小"的取舍：为何不用更重的调用做冒烟。

### C2 — Failure diagnosis（401/403/404 诊断树）
必答要素：
- [ ] 一棵显式决策树（文本树或表），根节点 = "connections 成功但 invoices 失败"。
- [ ] 必须覆盖题面列出的五类原因：token 过期 / scopes 不足 / 租户头或租户 ID 错误 / 权限未授予 / 环境配置差异。
- [ ] 401 / 403 / 404 分别映射到最可能的原因集合，并说明如何用一次可观测的检查区分（例如重取 token 后重试、比对 connections 返回的 tenantId、核对环境变量）。
- [ ] 每个叶子节点给出修复动作；给出"何时升级给谁"的边界。

### C3 — Incremental synchronisation（可续跑增量同步）
必答要素：
- [ ] 分页方案（页游标的获取与推进）。
- [ ] 变更窗口：modified-since（或等价机制）的定义、时间源选择（本地时钟 vs 服务器时间）、窗口重叠处理。
- [ ] 游标持久化时机：**页级提交后才推进**，杜绝"先推游标后写库"的丢失窗口。
- [ ] 去重：以 InvoiceID（服务端主键）为幂等键，upsert 语义 + updatedDate 冲突处理。
- [ ] 部分失败：页级断点、页内单条失败不阻塞整页、失败清单与重放策略。
- [ ] 安全重放：重放不产生副作用的前提（写入均幂等）、重放范围界定。
- [ ] 时钟与乱序：晚到的更新如何不被旧游标跳过。

### C4 — Rate limits（429 处理）
必答要素：
- [ ] 响应头的利用：遵循当前 Xero 文档所述的头信息与提示值，等待时长不凭空拍脑袋。
- [ ] 退避策略：指数退避 + **全抖动（full jitter）**公式，说明为什么抖动（惊群）。
- [ ] 并发上限：worker 侧信号量 / 令牌桶，限制在文档允许的配额之内并留余量。
- [ ] 重试预算：最大尝试次数 / 最大挂钟时间，超限后的处置（任务进死信队列 + 告警，而非静默丢弃）。
- [ ] 调度：限流事件反馈到任务队列优先级；跨租户公平性。
- [ ] **明确列出不应重试的错误**：4xx 非 429（401/403/404 等——修因而不是重试）、业务校验类 4xx；并说明 5xx 的有限重试边界。

### C5 — Data integrity（防重与对账）
必答要素：
- [ ] 防重复创建：以内部订单 ID 派生的确定性引用（如 InvoiceNumber 或自定义字段）作为天然幂等键；创建前先按引用查询 + 创建后回写引用。
- [ ] 超时重试路径：重试前先按引用查一次，命中即收养（adopt），不重发创建。
- [ ] "请求成功但响应丢失"的对账：周期性按引用反查 + 对账任务比对内部订单状态机（pending → confirmed → reconciled）。
- [ ] 边界：引用冲突 / 状态不一致时的人工介入入口与审计记录。
- [ ] 明确不依赖"创建接口自身的幂等性"这一未文档化假设（或标注为需文档核实）。

### C6 — Observability and security（可观测性与安全）
必答要素：
- [ ] 日志：结构化 JSON，字段含 correlation ID、租户 ID、endpoint、状态码、耗时、重试次数。
- [ ] 指标：限流命中数、同步滞后（lag）、各错误类别的速率、token 刷新失败数。
- [ ] 告警：滞后超阈值、认证失败激增、死信队列非空、配额水位。
- [ ] 关联标识：sync run ID + per-tenant ID 的传播规则（跨日志、跨服务）。
- [ ] **绝不能记录**：access/refresh token、授权码、发票中的个人敏感数据正文；日志中的租户数据最小化。
- [ ] 密钥存储与轮换：密管服务 / 加密静态存储、refresh token 轮换策略、泄露响应流程。
